# Agent Guide

This repo is the source of [progi-specjalizacje.pl](https://progi-specjalizacje.pl): a client-only React + TypeScript (Vite) dashboard of Polish medical residency recruitment results (CMKP). The app is backend-free; data are static JSON files generated at build time from CSVs in `source_data/`, which are themselves produced from official CMKP PDFs by `data_pipeline/`.

The former threshold/fill prediction model is archived in `archive/prediction/` and is not part of the site or the build.

## Quick Commands

```bash
npm install
npm run dev              # preprocess + SEO + Vite on http://127.0.0.1:5173/
npm run typecheck
npm run build            # preprocess + SEO + tsc + vite build -> dist/
npm run data:audit       # local data consistency audit (read-only, no network)
npm run data:download-places
npm run data:parse-places
npm run data:parse-results
```

The parsers need Python with `pdfplumber`.

## Project Map

```text
src/            React app
scripts/        build-time scripts (preprocess.js, generateHomepageSeo.js)
source_data/    site data: [wj]-YYYY_parsed.csv (results) + cmkp_places.csv (places)
data_pipeline/  CMKP PDF download/parse -> source_data/, plus audit.mjs
public/         static files; public/data/*.json is generated by preprocess.js
archive/        retired work (prediction model, SEO subpages, j-2022 round); not built
.agents/skills/ project skills (cmkp-data-refresh)
```

App:

- `src/App.tsx` renders the configured dashboard visuals into the CSS grid via `renderVisual()`.
- `src/config/dashboardLayout.ts` is the first place to change page arrangement, visual selection, KPI definitions, and pivot config.
- `src/config/specialtySearchFilter.ts` holds the medical/dental specialty split and the `LIMIT_SPECIALTY_SEARCH` flag.
- `src/data/reportData.ts` is the data access layer: report options, `fetchSpecialtyData` / `fetchSpecialtyPools` / `fetchSpecialtyPlaces` (fetching `public/data/*.json`), and `applyReportFilters()`. Components go through this layer.
- `src/data/reportMetadata.ts` is generated by `scripts/preprocess.js`; do not edit by hand.
- `src/state/filterStore.ts` owns global report filters; `src/state/calculatorStore.ts` owns the score calculator state (Zustand).
- `src/hooks/` holds the filtered-data subscriptions (`useFilteredRows`, `useFilteredPools`, `useFilteredPlaces`, `useSimulationScores`).
- `src/components/` contains report visuals and controls.
- `src/styles/theme.ts` owns text variants and color tokens; `src/styles/global.css` owns page, grid, control, KPI, and pivot styling.
- `src/types.ts` owns shared domain, filter, visual, and pivot types.
- `src/utils/formatters.ts` holds shared number/percent formatters.

Build scripts:

- `scripts/preprocess.js` reads `source_data/[wj]-YYYY_parsed.csv` and `source_data/cmkp_places.csv`, and writes `public/data/{specialty,pools,places}_<slug>.json` plus `src/data/reportMetadata.ts`.
- `scripts/generateHomepageSeo.js` fills the SEO block in `index.html` and writes `public/sitemap.xml` from `public/data/`.

Data pipeline (see `data_pipeline/README.md`):

- `data_pipeline/results/parse_smk_ranking.py` parses CMKP qualified-candidate PDFs from `data_pipeline/results/pdfs/` straight into `source_data/<round>_parsed.csv`. Its own `AGENTS.md` applies inside that directory. It used to be the separate repo `proginaspecke/cmkp_wyniki_parse`.
- `data_pipeline/places/` holds the CMKP places manifest, downloader, PDFs, and parser that write `source_data/cmkp_places.csv` and `cmkp_places_quality_report.json`.
- `data_pipeline/audit.mjs` checks the manifest, PDFs, places CSV, and round coverage.
- The `cmkp-data-refresh` skill in `.agents/skills/` drives the online freshness check and the update procedure.

## Architecture Rules

- Keep the app backend-free. Use local data and browser memory only unless the user explicitly asks for an integration.
- Keep components reading data through `src/data/reportData.ts`, so the source can change without changing component code.
- Add new filters to `ReportFilters`, `filterStore.ts`, `applyReportFilters()`, and the filter UI together.
- New data belongs in `source_data/` and must be produced by `data_pipeline/` scripts. Never hand-edit `source_data/`, `public/data/`, or `src/data/reportMetadata.ts`; regenerate them.
- `preprocess.js` treats only `[wj]-YYYY_parsed.csv` files in `source_data/` as recruitment rounds; keep that naming.
- A minimum accepted score from an incompletely filled pool is not a competitive threshold; threshold status depends on joining results with place counts.
- Add new visual types by extending `DashboardVisual` in `dashboardLayout.ts`, then update `renderVisual()` in `App.tsx`.
- Keep layout changes in `dashboardLayout.ts`; avoid hard-coding positions inside components.
- Keep TextBox style variants in `theme.ts` so typography stays consistent.
- Use shared formatters in `src/utils/formatters.ts` for displayed numbers and percentages.
- Do not import from or run code in `archive/` as part of the site. Its README explains how to restore something.

## Verification Checklist

Before handing off changes:

```bash
npm run typecheck
npm run build
```

For data changes, also run `npm run data:audit` and check `git diff source_data`: existing rounds should not change unless the parser was intentionally fixed.

For UI changes, also run `npm run dev` and verify:

- KPI values render.
- Filters change KPI and pivot values.
- The pivot table scrolls without header/body overlap.
- The layout remains usable below `980px` width.

## Deployment

`.github/workflows/deploy.yml` builds and publishes to GitHub Pages on push to `main`. The custom domain lives in `public/CNAME`. DNS details are in `README.md`.

## Notes For Future Agents

- Do not edit generated files in `dist/`, `node_modules/`, `public/data/`, or `public/sitemap.xml`.
- There are no automated unit tests for the app. Use `typecheck` and `build` as the minimum validation.
- The current pivot is `wojewodztwo` by `rekrutacja`, with the minimum score and median `ilosc_zakwalifikowanych_w_trybie`.
- The visual design is intentionally dashboard-like: dense, calm, and operational rather than a marketing landing page.
